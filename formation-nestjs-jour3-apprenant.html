Relations, chargement, transactions

Le concept

Une bibliothèque : un livre a été emprunté de nombreuses fois (un livre, plusieurs emprunts), et il est rangé dans plusieurs rayons, chaque rayon contenant plusieurs livres. Les tables se relient de même par des clés étrangères.

Les relations :

Relation Exemple En base
@ManyToOne / @OneToMany plusieurs leçons pour un cours une colonne courseId dans lessons
@ManyToMany + @JoinTable des livres et des genres une table de jointure livres_genres
entité de jointure un élève inscrit à un cours, avec sa date d'inscription (jour 3) une table enrollments à deux clés étrangères
@OneToOne un utilisateur et son profil une colonne unique

@ManyToOne est le côté qui porte la colonne ; @OneToMany, l'autre côté, n'ajoute rien en base. onDelete: 'CASCADE' : supprimer le cours supprime ses leçons, dans PostgreSQL même.

Charger les relations : par défaut, find ne charge pas les relations. relations: { lessons: true } ajoute un LEFT JOIN et remplit course.lessons.

Le problème N+1 : une requête pour la liste, puis une requête par élément pour ses relations : 100 cours, 101 requêtes. On le voit dans le journal SQL (logging: true) ; on le règle avec relations ou une requête qui regroupe.

Le QueryBuilder : pour les requêtes que find n'exprime pas (regroupements, sous-requêtes), createQueryBuilder('livre').leftJoin(…).select(…).groupBy(…) écrit le SQL pas à pas.

La transaction : plusieurs écritures qui réussissent ensemble ou échouent ensemble. dataSource.transaction(async (manager) => { … }) : si une écriture échoue, PostgreSQL annule les autres (ROLLBACK).

cascade : sur une relation, enregistre les objets liés avec l'objet principal (créer un cours et ses leçons d'un seul save).

En ESM : Relation<…> : deux entités liées s'importent l'une l'autre (Livre importe Emprunt, qui importe Livre). TypeScript enregistre le type de chaque propriété décorée au moment où la classe est créée ; en ESM, l'autre classe n'existe pas encore, et le démarrage s'arrête sur ReferenceError: Cannot access 'Livre' before initialization. La règle de TypeORM : chaque propriété de relation s'écrit Relation<Livre> ou Relation<Emprunt[]>, avec import type { Relation } from 'typeorm' (un type dans une signature décorée s'importe avec import type, comme pour l'erreur TS1272 du jour 1).

Quand s'en servir :

  • un élément qui appartient à un autre (une leçon à un cours, une commande à un client) : @ManyToOne et @OneToMany ;
  • des étiquettes partagées (genres, catégories) : @ManyToMany ; une entité de jointure dès que le lien porte une donnée (une date d'inscription, une quantité) ;
  • relations quand la réponse a besoin des éléments liés (une fiche avec ses leçons) ; rien sinon, pour garder les listes légères ;
  • un comptage ou un regroupement que find n'exprime pas : le QueryBuilder ;
  • une transaction dès qu'une opération écrit à deux endroits qui doivent rester d'accord : un prêt et le livre indisponible, une commande et son stock.

En résumé : @ManyToOne et sa colonne, @OneToMany en face ; relations pour charger ; une seule requête plutôt que N+1 ; une transaction pour les écritures liées ; en ESM, Relation<…> sur chaque propriété de relation.

Dans la vraie vie : les relations tous les jours ; le N+1 est la cause la plus fréquente d'une API lente, à chercher en premier dans le journal SQL ; les transactions dès qu'une opération écrit dans deux tables.

Les migrations

Le concept

Le carnet d'entretien d'un immeuble : chaque transformation (une cloison abattue, une fenêtre ajoutée) y est notée, datée, dans l'ordre ; on sait à tout moment dans quel état est le bâtiment et ce qui reste à faire. Une migration est une transformation du schéma de la base, écrite dans un fichier daté, appliquée une fois, dans l'ordre.

Pourquoi : synchronize modifie la base sans prévenir et peut effacer une colonne ; en équipe et en production, chaque changement doit être relu, appliqué de la même façon partout, et pouvoir être annulé.

La migration : une classe avec up() (appliquer : CREATE TABLE, ALTER TABLE…) et down() (annuler). TypeORM tient la liste de celles déjà appliquées dans une table migrations.

La CLI de TypeORM : elle tourne hors de Nest et a besoin de sa propre connexion, un DataSource dans src/database/data-source.ts, qui lit .env avec dotenv.

Commande Ce qu'elle fait
npm run migration:generate -- src/database/migrations/Nom compare les entités et la base, et écrit la migration qui manque
npm run migration:run applique les migrations pas encore appliquées
npm run migration:revert annule la dernière

En production : les migrations se lancent au déploiement, une fois, avant la nouvelle version de l'application (jour 3).

Quand s'en servir :

  • dès que la base contient des données à garder, ou qu'on travaille à plusieurs : les migrations, avec synchronize: false ;
  • une migration par changement du schéma (une colonne, une table, un index), générée puis relue avant d'être appliquée ;
  • migration:revert pour annuler la dernière en développement ; en production, on corrige plutôt par une nouvelle migration.

En résumé : synchronize: false, une migration par changement du schéma, générée, relue, appliquée par migration:run.

Dans la vraie vie : à chaque modification d'une entité ; la migration générée se relit comme du code, et se range dans Git avec le changement qui la demande.

Le cache

Le concept

Le menu du jour affiché à l'entrée d'une cantine : on ne demande pas au cuisinier à chaque client ce qu'il y a à manger ; on l'écrit une fois, et on le change quand le menu change. Un cache garde une réponse coûteuse pour la redonner sans refaire le travail.

@nestjs/cache-manager : CacheModule.register() dans un module crée un cache en mémoire ; CacheInterceptor, un intercepteur fourni par Nest, garde la réponse d'une route GET, par adresse complète (?page=2 et ?page=3 sont deux entrées). @CacheTTL(30_000) : sa durée de vie, en millisecondes.

L'invalidation : après une écriture, la liste gardée est fausse. On vide le cache (cache.clear()) ou on attend la fin de sa durée de vie. Choisir la durée est un compromis : plus elle est longue, plus l'API est rapide et plus les données peuvent être en retard.

Redis : le cache en mémoire vit dans un seul processus ; avec plusieurs instances de l'API, chacune a le sien. On partage alors un cache Redis, un serveur de données en mémoire, branché sur le même CacheModule (paquet @keyv/redis).

Quand s'en servir :

  • une route GET lente ou coûteuse dont la réponse change peu : un catalogue, des statistiques, l'appel à un service extérieur ;
  • jamais sur une réponse propre à chaque utilisateur (son panier, son profil) : la clé du cache est l'adresse, pas la personne ;
  • après une écriture : vider le cache, ou accepter des données en retard le temps de leur durée de vie ;
  • Redis dès que l'API tourne en plusieurs instances.

En résumé : CacheInterceptor sur une route GET qui coûte cher, une durée de vie choisie, le cache vidé après une écriture.

Dans la vraie vie : de temps en temps, sur ce qui coûte cher et change peu (un catalogue, l'appel à un service extérieur) ; avec Redis dès qu'il y a plusieurs instances.

L'authentification

Authentification, autorisation et jetons

Le concept

Le badge d'un salon professionnel : à l'accueil, on montre sa pièce d'identité une fois (l'authentification : qui êtes-vous ?) ; on reçoit un badge, qu'on présente ensuite à chaque stand. Le badge dit aussi « exposant » ou « visiteur » : certains stands sont réservés aux exposants (l'autorisation : avez-vous le droit ?).

Session ou jeton :

Session (côté serveur) Jeton (JWT)
Ce que garde le client un cookie avec un numéro de session le jeton lui-même
Ce que garde le serveur la session en mémoire ou en base rien : il vérifie la signature du jeton
Plusieurs serveurs il faut partager les sessions (Redis…) chacun vérifie avec le même secret
Déconnecter tout de suite on supprime la session difficile : le jeton reste valable jusqu'à son expiration
Usage courant sites web classiques API appelées par une application web ou mobile

Le JWT (JSON Web Token) : trois parties séparées par des points, en-tête.contenu.signature. L'en-tête et le contenu sont du JSON encodé en base64url : lisibles par n'importe qui. La signature est calculée avec un secret que seul le serveur connaît : un jeton modifié ou signé avec un autre secret est refusé. On ne met donc rien de secret dans le contenu (un identifiant et un rôle, pas un mot de passe).

Les champs standard : sub (subject, le compte), iat (issued at, émis à), exp (expiration), en secondes depuis 1970.

Côté client : le jeton s'envoie dans l'en-tête Authorization: Bearer <le jeton>. Une application web le garde en mémoire (ou dans un cookie httpOnly posé par le serveur) ; dans localStorage, un script injecté dans la page pourrait le lire.

Les règles : une durée de vie courte (15 minutes à une heure), un secret long et hors du code, HTTPS partout. Pour ne pas redemander le mot de passe toutes les heures, on ajoute un jeton de rafraîchissement, plus long, qui sert seulement à obtenir un nouveau jeton : hors du programme, cité en fin de journée.

En résumé : on s'authentifie une fois, on reçoit un jeton signé, on le présente à chaque requête ; le serveur vérifie la signature et lit le rôle.

Dans la vraie vie : tous les jours ; la plupart des API appelées par une application web ou mobile utilisent un JWT, souvent fourni par un service d'identité (Keycloak, Auth0, Entra ID) plutôt que fabriqué par l'API elle-même. Le principe et le guard qui le vérifie sont les mêmes.

Des comptes, et des mots de passe hachés

Le concept

Le vestiaire d'un théâtre ne garde pas votre nom, il vous donne un ticket ; mais pour un mot de passe, on ne garde même pas le ticket : on garde une empreinte, à partir de laquelle on ne peut pas retrouver le mot de passe, mais avec laquelle on peut vérifier celui qu'on tape.

Hacher, pas chiffrer : un mot de passe chiffré peut être déchiffré (avec la clé) ; un mot de passe haché ne peut pas être retrouvé. À la connexion, on hache ce que tape l'utilisateur et on compare.

bcrypt : l'algorithme de hachage de mots de passe le plus répandu avec Node.js. Il ajoute un sel tiré au hasard (deux comptes avec le même mot de passe n'ont pas la même empreinte) et un coût : 10 signifie 2^10 tours de calcul, assez lent pour décourager un attaquant qui essaierait des milliards de mots de passe.

La table des comptes : l'adresse unique (unique: true) ; le hash dans une colonne marquée select: false, jamais lue par défaut, pour qu'il ne parte jamais dans une réponse par mégarde ; le rôle dans un type énuméré (enum) de PostgreSQL.

L'inscription : refuser une adresse déjà prise (409), hacher, enregistrer, et renvoyer le compte sans le hash. On ne laisse pas choisir le rôle administrateur à l'inscription.

En résumé : bcrypt (hash, compare), coût 10 à 12 ; le hash en select: false ; l'inscription renvoie le compte sans hash.

Dans la vraie vie : on écrit l'inscription une fois par projet, ou on la confie à un service d'identité. Argon2 est l'autre algorithme recommandé aujourd'hui ; MD5 et SHA-256 seuls ne conviennent pas aux mots de passe (trop rapides).

La connexion et le jeton

Le concept

Le guichet qui vérifie votre pièce d'identité et vous remet le badge : la route de connexion compare le mot de passe et, s'il est bon, signe un jeton.

JwtModule.registerAsync : le module de @nestjs/jwt, configuré avec le secret lu dans la configuration et la durée de vie des jetons (expiresIn: '1h'). Il fournit JwtService : signAsync(contenu) fabrique le jeton.

Le secret : une longue valeur aléatoire, dans .env, vérifiée au démarrage (32 caractères au moins). Qui le connaît peut fabriquer des jetons valides : il ne va jamais dans le code ni dans Git.

Un seul message d'erreur : adresse inconnue ou mauvais mot de passe, la réponse est la même (« Adresse ou mot de passe incorrect », 401). Sinon, un attaquant apprendrait quelles adresses ont un compte.

200, pas 201 : une connexion ne crée rien sur le serveur ; @HttpCode(200) sur le POST.

En résumé : bcrypt.compare, puis jwtService.signAsync({ sub, email, role }) ; un message unique pour tous les échecs.

Dans la vraie vie : une fois par projet ; la durée de vie du jeton et la façon de le renouveler se décident avec l'équipe sécurité.

Guards et routes publiques

TP

Un guard pour toute l'API, et des routes publiques

Le concept

Un immeuble de bureaux où toutes les portes demandent le badge, sauf l'accueil et la cafétéria, signalées par un panneau « libre accès ». Plutôt que de poser un lecteur de badge porte par porte (et d'en oublier une), on protège tout, et on étiquette les exceptions.

Le guard global : déclaré comme provider avec le jeton APP_GUARD (de @nestjs/core), un guard s'applique à toutes les routes de l'application, y compris celles qu'on écrira plus tard. C'est plus sûr qu'un @UseGuards à ne pas oublier sur chaque contrôleur.

SetMetadata et Reflector : SetMetadata('isPublic', true) colle une étiquette sur une méthode ou un contrôleur ; le guard la lit avec reflector.getAllAndOverride('isPublic', [méthode, contrôleur]). On en fait un décorateur à soi, @Public(), en une ligne. Reflector.createDecorator<T>() fabrique d'un coup le décorateur et son étiquette, typés : la médiathèque s'en sert.

Une étiquette pour un rôle : le même mécanisme sert à demander un rôle. Un compte connecté qui n'a pas le rôle demandé reçoit 403 (Forbidden, ForbiddenException) ; sans jeton, c'est 401. La médiathèque l'essaie ci-dessous ; LearnHub le fera dans la partie suivante.

createParamDecorator : fabrique un décorateur de paramètre, comme @Body() : @CurrentUser() donne à la méthode le compte que le guard a rangé dans la requête.

Le guard JWT : lit l'en-tête Authorization: Bearer <jeton>, le vérifie (jwtService.verifyAsync : signature et expiration), range son contenu dans req.user ; sinon, 401.

Les deux 401 : « Jeton manquant » (pas d'en-tête) et « Jeton invalide ou expiré » (signature fausse, jeton périmé). Le client réagit pareil : il renvoie l'utilisateur vers la connexion.

En résumé : un guard global (APP_GUARD) qui exige un jeton ; @Public() pour les exceptions ; @CurrentUser() pour lire le compte.

Dans la vraie vie : une fois par projet ; ensuite, à chaque nouvelle route, on se demande seulement si elle doit être publique. Beaucoup de projets passent par @nestjs/passport et sa stratégie JWT : le principe et le résultat sont les mêmes.

Autorisation par rôles

TP

Les rôles, et l'auteur d'une ressource

Le concept

Dans un hôpital, le badge d'un infirmier ouvre le service de soins, pas la pharmacie ; et même le médecin n'ouvre que les dossiers de ses patients. Deux niveaux de contrôle : le rôle (quel type de compte peut faire cette action ?) et la ressource (ce compte a-t-il des droits sur cet objet-là ?).

@Roles() et RolesGuard : @Roles(Role.Teacher, Role.Admin) colle la liste des rôles autorisés sur une méthode ; un second guard global, RolesGuard, la compare au rôle du jeton : 403 si le rôle manque. Il est déclaré après le guard JWT : les guards globaux passent dans l'ordre où ils sont déclarés, et req.user doit déjà être rempli.

Le contrôle de la ressource : il se fait dans le service, qui connaît le cours : « l'auteur du cours, ou un administrateur ». C'est le premier risque de la liste OWASP des API : une API qui vérifie le rôle, mais pas à qui appartient la ressource, laisse un formateur modifier les cours des autres.

401 ou 403 : 401, on ne sait pas qui vous êtes (pas de jeton, jeton invalide) ; 403, on sait, et vous n'avez pas le droit.

Les erreurs classiques : vérifier les droits seulement dans l'application web (l'API reste ouverte à curl) ; lire le rôle dans le corps de la requête au lieu du jeton ; oublier le contrôle de la ressource.

En résumé : @Roles() + RolesGuard pour le type de compte ; une vérification dans le service pour l'objet ; 401 sans identité, 403 sans droit.

Dans la vraie vie : les rôles tous les jours, dès qu'une application a des profils ; le contrôle de la ressource aussi, et c'est lui qu'on oublie.

Durcir l'API

TP

Les risques courants, et trois protections

Le concept

Une maison qui a de bonnes serrures (les jetons, les rôles) peut encore avoir une fenêtre ouverte. L'OWASP (Open Worldwide Application Security Project, une fondation qui recense les failles les plus fréquentes) publie la liste des dix risques les plus courants des API : l'OWASP API Security Top 10, édition 2023, la dernière parue. On s'en sert comme d'une liste de contrôle :

Risque (OWASP API 2023) En clair Dans LearnHub
API1 · Broken Object Level Authorization modifier l'objet d'un autre en changeant l'identifiant dans l'adresse assertCanEdit : seul l'auteur modifie son cours (3.4-A)
API2 · Broken Authentication deviner ou voler un compte bcrypt, un seul message d'erreur à la connexion (3.2) ; la limite de débit, ci-dessous
API3 · Broken Object Property Level Authorization envoyer un champ interdit (son rôle), lire un champ secret (le hash) whitelist du ValidationPipe (jour 1) ; role limité à élève ou formateur ; le hash jamais lu (select: false)
API4 · Unrestricted Resource Consumption épuiser le serveur : des milliers de requêtes, des pages géantes 50 cours par page au plus (jour 2) ; la limite de débit, ci-dessous
API5 · Broken Function Level Authorization appeler une route réservée à un autre rôle RolesGuard (3.4-A)
API6 · Unrestricted Access to Sensitive Business Flows automatiser un parcours sensible (inscriptions factices en masse) selon le métier : limites, vérifications
API7 · Server Side Request Forgery faire appeler par le serveur une adresse choisie par l'attaquant LearnHub n'appelle aucune adresse reçue
API8 · Security Misconfiguration réglages par défaut, erreurs trop bavardes, en-têtes manquants erreurs sans détail technique (jour 2) ; Helmet et CORS, ci-dessous
API9 · Improper Inventory Management des routes oubliées, d'anciennes versions encore ouvertes Swagger documente toutes les routes
API10 · Unsafe Consumption of APIs croire sans vérifier les réponses d'une autre API à vérifier dès qu'on appelle une API extérieure

Helmet : un middleware qui ajoute des en-têtes de sécurité à chaque réponse. Par exemple X-Content-Type-Options: nosniff (le navigateur ne devine pas le type d'un fichier), Strict-Transport-Security (le navigateur n'utilise plus que HTTPS pour ce site), Content-Security-Policy (d'où une page a le droit de charger ses scripts). Une ligne : app.use(helmet()).

CORS (Cross-Origin Resource Sharing, le partage entre origines) : par défaut, un navigateur interdit à une page de http://localhost:5173 de lire les réponses d'une API sur http://localhost:3010 (une autre origine : adresse et port). app.enableCors({ origin: [...] }) dit au navigateur quelles origines ont le droit. CORS ne protège que des navigateurs : curl ou un script l'ignorent ; la vraie protection reste le jeton.

La limite de débit (@nestjs/throttler) : au-delà d'un nombre de requêtes par minute et par adresse IP, l'API répond 429 Too Many Requests. Une limite générale, 100 par minute (ThrottlerModule et ThrottlerGuard en guard global), et une plus stricte sur la connexion, 5 par minute, avec le décorateur @Throttle() : personne ne devine un mot de passe en essayant des milliers de fois.

En résumé : l'OWASP API Top 10 comme liste de contrôle ; Helmet pour les en-têtes, CORS pour les navigateurs, @nestjs/throttler contre les rafales.

Dans la vraie vie : Helmet et CORS dans chaque API, réglés une fois. La limite de débit est souvent aussi posée devant l'API (passerelle d'API, répartiteur de charge, pare-feu applicatif) ; avec plusieurs copies de l'API, les compteurs se partagent dans un stockage commun, par exemple Redis.

Les tests unitaires

TP

Tester une classe seule : Vitest et les faux

Le concept

Un moteur se teste sur un banc d'essai, sans la voiture : on le branche à de faux capteurs, on lui envoie des valeurs choisies, on mesure. Un test unitaire fait pareil avec une classe : on la sort de l'application, on remplace ce dont elle dépend par des faux, et on vérifie ce qu'elle fait.

Le test automatisé : un petit programme qui appelle votre code et vérifie le résultat. On le relance à chaque modification : s'il échoue, on sait tout de suite ce qu'on a cassé.

La pyramide des tests : beaucoup de tests unitaires (une classe seule, quelques millisecondes), moins de tests d'intégration (plusieurs pièces ensemble), peu de tests de bout en bout (toute l'API, interrogée comme par un client, plus lents ; la partie suivante).

Vitest : l'outil qui trouve les fichiers *.spec.ts, les exécute et affiche le bilan. describe('…', …) regroupe des tests ; it('…', …) est un test ; expect(valeur) vérifie : toBe (la même valeur), toEqual (le même contenu), rejects.toThrow(…) (une promesse qui échoue avec cette erreur).

Les faux (mocks) : vi.fn() fabrique une fonction simulée. On choisit ce qu'elle renvoie (mockResolvedValue(…) : une promesse qui réussit avec cette valeur) et on vérifie comment elle a été appelée (toHaveBeenCalledWith(…), not.toHaveBeenCalled()). vi.mock('bcrypt') remplace toutes les fonctions d'une bibliothèque.

Test.createTestingModule : un module Nest construit pour le test, avec la vraie classe testée et un faux pour chacune de ses dépendances : { provide: …, useValue: faux }, comme les providers du jour 1. Le repository de Course se range sous un jeton que donne getRepositoryToken(Course).

Préparer, agir, vérifier (Arrange, Act, Assert) : les trois temps de chaque test.

La couverture : npm run test:cov mesure la part du code exécutée par les tests, fichier par fichier.

En résumé : un test par règle métier, la classe seule, ses dépendances remplacées par des faux ; npm test à chaque modification.

Dans la vraie vie : chaque jour. On teste d'abord les services, où sont les règles (droits, calculs, cas d'erreur), plutôt que les contrôleurs, qui ne font que transmettre. La couverture est un indicateur : une règle importante sans test compte plus qu'un pourcentage. Le programme cite Jest : depuis la version 12, la CLI de NestJS crée les projets ESM avec Vitest, celui de nos deux projets. describe, it et expect s'écrivent de la même façon, et jest.fn() devient vi.fn().

Les tests de bout en bout

TP

Tester l'API comme un client : Supertest

Le concept

Après le banc d'essai, l'essai sur piste : toute la voiture, sur un circuit fermé. Un test de bout en bout (e2e, end-to-end) démarre la vraie application (modules, guards, pipes, filtre, base de données) et lui envoie de vraies requêtes HTTP.

Supertest : envoie une requête à l'application sans ouvrir de port, puis vérifie la réponse : request(app.getHttpServer()).post('/api/courses').set('Authorization', …).send({ … }).expect(201).

L'application de test : Test.createTestingModule({ imports: [AppModule] }), puis createNestApplication(). app.init() la démarre, app.close() l'arrête et ferme la connexion à PostgreSQL.

Une base pour les tests : learnhub_test, jamais celle de développement. En test seulement, TypeORM la vide à chaque lancement (dropSchema) et crée les tables d'après les entités (synchronize) : chaque lancement part d'une base propre.

Les mêmes réglages qu'en vrai : le préfixe api, le ValidationPipe, le filtre et Helmet sont posés dans main.ts, que les tests ne lancent pas. On les range dans une fonction, configureApp, appelée par main.ts et par les tests.

--no-file-parallelism : Vitest lance d'habitude les fichiers de test en même temps, chacun de son côté. Deux fichiers qui vident la même base au même moment se gênent ; --no-file-parallelism les lance l'un après l'autre.

En résumé : la vraie application, une base de test vidée à chaque lancement, Supertest pour les requêtes, un fichier après l'autre.

Dans la vraie vie : quelques scénarios sur les parcours qui comptent (connexion, droits, paiement), lancés à chaque envoi par l'intégration continue avec une base PostgreSQL de service. Ils sont plus lents que les tests unitaires : on en écrit moins. Certaines équipes démarrent une base neuve dans Docker à chaque lancement (Testcontainers).

Docker

TP

Une image pour l'API, Compose pour la lancer avec sa base

Le concept

Un conteneur maritime se charge de la même façon sur n'importe quel bateau, quoi qu'il contienne. Une image Docker contient l'API, Node.js et ses bibliothèques : elle tourne de la même façon sur votre poste, sur le serveur d'intégration continue et en production. Fini le « chez moi, ça marche ».

L'image et le conteneur : l'image est un modèle figé (un système minimal, Node.js, votre code compilé) ; un conteneur est une image qui tourne.

Le Dockerfile : la recette de l'image, une instruction par ligne : FROM (l'image de départ), WORKDIR (le dossier de travail), COPY (copier des fichiers), RUN (lancer une commande pendant la construction), USER, EXPOSE, HEALTHCHECK, CMD (la commande lancée au démarrage du conteneur).

Les étapes multiples (multi-stage) : une première étape compile, avec tous les outils de développement ; la seconde repart d'une image neuve et ne reçoit que le résultat (COPY --from=build). L'image finale est plus petite, et contient moins de logiciels qui pourraient avoir des failles.

Le .dockerignore : ce qui n'entre pas dans l'image : node_modules (réinstallés dans l'image), .env (un secret n'entre jamais dans une image).

Un utilisateur non administrateur : USER node. Si l'API est attaquée, l'attaquant n'est pas administrateur (root) du conteneur.

Le healthcheck : une commande que Docker lance à intervalles réguliers (ici, appeler /api/health) ; le conteneur passe « healthy » (en bonne santé) ou « unhealthy ». Les plateformes d'hébergement font la même chose pour remplacer une copie malade.

Docker Compose : un fichier compose.yaml décrit plusieurs conteneurs (l'API et PostgreSQL), leurs variables, leur réseau et leurs volumes ; docker compose up -d les lance tous, en arrière-plan (-d), et --wait attend qu'ils soient en bonne santé avant de rendre la main. Un volume est un dossier géré par Docker, qui survit au conteneur : les données de PostgreSQL ne disparaissent pas à l'arrêt.

En résumé : un Dockerfile en deux étapes, un .dockerignore, un utilisateur sans droits, un healthcheck ; Compose pour lancer l'API avec sa base.

Dans la vraie vie : toutes les équipes qui déploient dans un cloud livrent des images. Compose sert surtout sur les postes (la base de développement, une démonstration) ; en production, c'est la plateforme qui lance les conteneurs (Amazon ECS, Kubernetes…). Podman remplace parfois Docker, avec les mêmes fichiers.

Exercice · dans learnhub

--wait : Compose rend la main quand les deux conteneurs sont « healthy ». Sans lui, docker compose ps lancé aussitôt affiche « health: starting », et le curl reçoit une réponse vide : l'API démarre encore. STATUS : healthy pour les deux conteneurs. DISK USAGE est la place occupée sur le disque, CONTENT SIZE celle des couches compressées, envoyées à un registre. Pour tout arrêter : docker compose down (le volume et ses données restent) ; docker compose down -v efface aussi les données.

La mise en production

L'intégration continue, puis AWS

Le concept

Une chaîne d'usine contrôle chaque pièce avant l'emballage. L'intégration continue (CI, continuous integration) fait de même avec le code : à chaque envoi sur GitHub, une machine neuve installe le projet, vérifie le code, lance les tests et construit l'image. Si une étape échoue, l'envoi est marqué en rouge, et personne ne déploie.

GitHub Actions : le service d'intégration continue de GitHub. Un fichier .github/workflows/ci.yml dit quand se lancer (on), sur quelle machine (runs-on), avec quels services (une base PostgreSQL), et les étapes (steps).

AWS : où tourne LearnHub en production

Ouvrir un magasin dans un centre commercial plutôt que construire le bâtiment : le centre fournit les murs, la sécurité, l'électricité ; on paie à l'usage. AWS (Amazon Web Services) fournit de la même façon des services gérés : on y dépose l'image, AWS la fait tourner.

Besoin Service AWS Ce qu'il fait pour LearnHub
Ranger les images Amazon ECR (Elastic Container Registry) le registre où la CI dépose learnhub-api, une version par commit
Faire tourner les conteneurs Amazon ECS sur AWS Fargate lance deux copies de l'image sans serveur à gérer ; remplace une copie malade (healthcheck)
La base Amazon RDS for PostgreSQL PostgreSQL géré : sauvegardes, mises à jour, une copie de secours dans une autre zone (Multi-AZ)
Les secrets AWS Secrets Manager JWT_SECRET et le mot de passe de la base, donnés au conteneur à son démarrage, jamais écrits dans l'image
L'entrée Application Load Balancer HTTPS, puis répartit les requêtes entre les copies en bonne santé (/api/health)
Les droits AWS IAM (les rôles) la tâche a le droit de lire ses secrets et d'écrire ses journaux, rien d'autre
Les journaux Amazon CloudWatch Logs les lignes du Logger de chaque copie, au même endroit

Les migrations en production : notre image les applique au démarrage, ce qui suffit avec une seule copie. Avec deux copies, deux démarrages simultanés lanceraient les mêmes migrations : on les applique plutôt une fois, dans une tâche ECS ponctuelle (la même image, avec la commande migration:run), avant de déployer la nouvelle version. Une migration reste compatible avec la version précédente du code, qui tourne encore pendant le déploiement : ajouter une colonne en une fois ; la renommer en deux versions.

Un déploiement : la CI pousse l'image dans ECR ; la tâche ponctuelle applique les migrations ; ECS remplace les copies une à une, et le répartiteur n'envoie des requêtes qu'aux nouvelles copies en bonne santé.

Les coûts : chaque service se paie à l'usage : Fargate au processeur et à la mémoire, par seconde ; RDS à l'heure d'instance et au stockage ; le répartiteur à l'heure et au trafic ; Secrets Manager au secret et par mois. Le calculateur de prix d'AWS donne le total d'une architecture ; choisir la région Europe (Paris), eu-west-3. Les autres clouds ont les mêmes briques : Google Cloud Run, Azure Container Apps ; en France, Scaleway ou Clever Cloud.

En résumé : une image, testée par la CI, rangée dans ECR, lancée par ECS Fargate derrière un répartiteur, avec RDS pour la base et Secrets Manager pour les secrets ; les migrations dans une tâche à part.

Dans la vraie vie : on décrit cette architecture dans des fichiers (Terraform, AWS CDK) plutôt qu'à la main dans la console d'AWS, pour pouvoir la recréer et la relire. Sans compte AWS, on ne déploie pas en direct aujourd'hui : un compte demande une carte bancaire, et ces services sont facturés dès la première heure.

Quiz oral

  1. Quelle différence entre 401 et 403 ? (401 : on ne sait pas qui vous êtes, pas de jeton ou un jeton invalide ; 403 : on le sait, et vous n'avez pas le droit.)
  2. Pourquoi ne jamais enregistrer un mot de passe tel quel ? (Une base volée donnerait tous les mots de passe ; on garde un hash bcrypt, qu'on compare sans pouvoir le défaire.)
  3. Que contient un jeton JWT, et que peut en faire celui qui le lit ? (Un en-tête, un contenu lisible par tous, une signature ; le lire ne permet pas de le modifier sans le secret, d'où : rien de secret dedans.)
  4. Pourquoi le guard des rôles est-il déclaré après le guard JWT ? (Les guards globaux passent dans l'ordre de déclaration ; le guard des rôles lit req.user, que le guard JWT remplit.)
  5. Pourquoi des faux dans un test unitaire ? (Pour tester la classe seule, vite, sans base ni réseau, et choisir chaque cas : compte trouvé, introuvable, mauvais mot de passe.)
  6. Pourquoi deux étapes dans le Dockerfile ? (La première compile avec tous les outils ; la seconde ne garde que le résultat : une image plus petite, avec moins de failles possibles.)
