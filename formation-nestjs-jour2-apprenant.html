Le trajet d'une requête

Les étapes d'une requête dans Nest

Le concept

Le contrôle de sécurité d'un aéroport : on passe d'abord l'enregistrement, puis le contrôle des papiers, le portique, le contrôle des bagages, avant d'embarquer ; et un même agent peut vous accompagner du départ à l'arrivée. Une requête traverse de même des étapes, toujours dans le même ordre, avant d'atteindre la méthode du contrôleur, puis sur le chemin du retour.

Le middleware : la première étape, avant que Nest sache quelle méthode répondra. Il voit la requête et la réponse d'Express : journaliser, ajouter un en-tête, refuser tôt.

Le guard : décide si la requête a le droit de continuer (oui ou non). Il sait quelle méthode va répondre. C'est l'outil de l'authentification et des rôles (jour 3).

L'intercepteur : enveloppe la méthode, avant et après : mesurer une durée, transformer la réponse, couper ce qui est trop long.

Le pipe : vérifie ou transforme un paramètre juste avant la méthode : ParseUUIDPipe, ValidationPipe.

Le filtre d'exception : reçoit toute erreur levée en chemin et fabrique la réponse d'erreur.

Les niveaux : chaque étape se branche à trois niveaux. Sur une méthode (@UseGuards(…) au-dessus de la méthode), sur tout un contrôleur (au-dessus de la classe), ou sur toute l'application (app.useGlobalPipes(…) dans main.ts, comme ValidationPipe jeudi). Les middlewares, eux, se branchent dans un module, par adresse.

Quand s'en servir :

  • toucher à toutes les requêtes, avant même de savoir qui va répondre (identifiant de requête, journal brut, en-têtes) : un middleware ;
  • dire oui ou non selon qui appelle (clé d'API, connexion, rôle) : un guard ;
  • convertir ou refuser une valeur reçue (un identifiant, un corps) : un pipe ;
  • agir avant et après la méthode, ou changer la réponse (durée, enveloppe, cache, délai) : un intercepteur ;
  • donner une forme aux erreurs : un filtre d'exception.

En résumé : middleware, guard, intercepteur (avant), pipe, méthode, intercepteur (après) ; un filtre pour les erreurs.

Dans la vraie vie : on ne les écrit pas tous les jours, mais toute API d'entreprise en a quelques-uns, écrits une fois : un identifiant de requête, un journal, un guard d'authentification, un filtre d'erreurs. Savoir dans quel ordre ils passent évite de chercher longtemps pourquoi l'un ne voit pas ce qu'a fait l'autre.

Les middlewares

TP

Le middleware : agir sur toutes les requêtes

Le concept

L'accueil d'un immeuble, qui note l'heure d'arrivée de chaque visiteur et lui remet un badge avant qu'il monte, quel que soit l'étage où il va.

Le middleware fonction : une fonction (req, res, next), comme en Express. Elle fait son travail, puis appelle next() pour passer la main ; sans next(), la requête reste bloquée.

Pratique pour un traitement simple, sans dépendance.

Le middleware classe : une classe @Injectable() qui implémente NestMiddleware et sa méthode use(req, res, next). Elle peut recevoir des services par son constructeur.

Le brancher : un module implémente NestModule et sa méthode configure(consumer) ; consumer.apply(LeMiddleware).forRoutes(…) dit sur quelles adresses : un contrôleur (forRoutes(LivresController)) ou toutes (forRoutes('{*path}')).

{*path}, la syntaxe d'Express 5 : « toutes les adresses » s'écrivait '*' ; Express 5 demande un nom au joker. forRoutes('*') marche encore, avec un avertissement dans le terminal et une conversion automatique.

Quand s'en servir :

  • un traitement qui ne dépend pas de la méthode visée : identifiant de requête, journal de chaque appel, en-têtes de sécurité ;
  • un outil d'Express déjà écrit (Helmet, compression) : il se branche tel quel, comme middleware ;
  • la fonction quand il n'a besoin de rien ; la classe quand il lui faut un service (configuration, journal) ;
  • pas pour refuser selon les droits : le middleware ne sait pas quelle méthode va répondre ; c'est le rôle du guard.

En résumé : (req, res, next) et next() ; configure() et forRoutes() pour le brancher.

Dans la vraie vie : de temps en temps ; les middlewares viennent souvent de bibliothèques (Helmet, au jour 3, est un middleware). On en écrit pour un identifiant de requête, un journal d'accès, la lecture d'un en-tête maison.

Les pipes

TP

Les pipes intégrés et les pipes maison

Le concept

Le contrôle des bagages : chaque bagage passe sur le tapis avant l'avion ; il est accepté tel quel, transformé (on retire une bouteille), ou refusé. Un pipe reçoit un paramètre, juste avant la méthode, et le renvoie transformé, ou lève une exception (400).

Les pipes intégrés :

Pipe Ce qu'il fait
ParseIntPipe, ParseFloatPipe, ParseBoolPipe texte → nombre, booléen ; sinon 400
ParseUUIDPipe vérifie un identifiant UUID
ParseEnumPipe, ParseArrayPipe, ParseDatePipe une valeur d'une liste, un tableau, une date
DefaultValuePipe une valeur par défaut quand le paramètre manque
ValidationPipe vérifie un DTO (jeudi)

Le pipe maison : une classe @Injectable() qui implémente PipeTransform et sa méthode transform(valeur). Elle peut recevoir des services : un pipe qui transforme un identifiant en livre, ou répond 404.

Les pipes à la suite : @Param('id', ParseIntPipe, LivreParIdPipe) : le premier donne un nombre au second, qui donne un livre à la méthode.

Le piège de l'ordre : les pipes globaux passent avant ceux du paramètre. Avec ValidationPipe et transform: true, un paramètre déclaré number est déjà converti : ?limite=deux devient NaN, et DefaultValuePipe remplace NaN par sa valeur par défaut, sans erreur. Pour des paramètres de liste (page, limite), un DTO de requête vérifie mieux : c'est l'exercice 2.8-A.

Quand s'en servir :

  • un paramètre d'adresse à convertir ou à vérifier (:id, ?page=) : un pipe intégré (ParseIntPipe, ParseUUIDPipe, DefaultValuePipe) ;
  • un corps de requête : ValidationPipe et un DTO, pas un pipe par champ ;
  • la même transformation dans plusieurs routes (un identifiant qui devient un livre) : un pipe maison ;
  • pas pour une règle qui dépend de l'utilisateur connecté : c'est le guard.

En résumé : un pipe par paramètre, intégré le plus souvent ; un pipe maison pour une transformation qui revient partout.

Dans la vraie vie : ParseIntPipe, ParseUUIDPipe et ValidationPipe tous les jours ; un pipe maison de temps en temps.

Les guards

Le guard : laisser passer ou refuser

Le concept

Le contrôle des papiers avant l'embarquement : l'agent regarde votre billet et dit oui ou non. Il sait pour quel vol vous vous présentez.

Le guard : une classe @Injectable() qui implémente CanActivate et sa méthode canActivate(context), qui renvoie true (on passe) ou false (403 Forbidden), ou lève sa propre exception (401 Unauthorized, avec un message).

ExecutionContext : ce que reçoit le guard. context.switchToHttp().getRequest() donne la requête ; context.getHandler() et context.getClass(), la méthode et le contrôleur qui vont répondre : un guard peut ainsi lire les décorateurs de la méthode (jour 3, @Public() et @Roles()).

Le brancher : @UseGuards(MonGuard) sur une méthode ou un contrôleur, ou pour toute l'application (jour 3).

Quand s'en servir :

  • savoir si l'appelant a le droit d'atteindre la méthode : connexion, rôle, clé d'API, abonnement actif ;
  • c'est CanActivate d'Angular, mais côté serveur : celui d'Angular n'empêche que la navigation dans le navigateur, seul celui du serveur protège les données ;
  • false donne 403 ; pour 401 (pas connecté) ou un message précis, lever l'exception soi-même ;
  • pas pour transformer une donnée (pipe) ni pour mesurer une durée (intercepteur).

En résumé : canActivate répond oui ou non ; le guard est la place de l'authentification et des droits.

Dans la vraie vie : tous les jours, mais on les écrit une fois par projet : le guard d'authentification et celui des rôles, vendredi.

Les intercepteurs

TP

Avant et après la méthode : l'intercepteur

Le concept

Le chronométreur d'une course : il déclenche le chrono au départ, l'arrête à l'arrivée, et peut même changer le dossard du coureur avant qu'il franchisse la ligne. Un intercepteur agit avant la méthode du contrôleur et après, sur ce qu'elle renvoie.

intercept(context, next) : la méthode d'un intercepteur (@Injectable() qui implémente NestInterceptor). Ce qui est écrit avant next.handle() se passe avant la méthode ; next.handle() lance la méthode et renvoie sa réponse à venir.

RxJS, en deux secondes : next.handle() renvoie un Observable, un tuyau par lequel la réponse arrivera. .pipe(…) y branche des opérateurs, appliqués quand la réponse passe :

Opérateur Ce qu'il fait Usage
tap(() => …) regarde passer la réponse sans la changer journaliser, mesurer une durée
map((données) => …) remplace la réponse par ce que renvoie la fonction envelopper, renommer, retirer un champ
timeout(2000) lève une erreur si rien n'arrive à temps ne pas attendre indéfiniment
catchError((erreur) => …) remplace une erreur par une autre traduire une erreur en exception HTTP

Le brancher : @UseInterceptors(…) sur une méthode ou un contrôleur ; app.useGlobalInterceptors(new …()) dans main.ts pour toute l'application.

Quand s'en servir :

  • agir avant et après la méthode : mesurer une durée, journaliser une requête réussie ;
  • changer la forme de toutes les réponses (une enveloppe commune) ou en retirer des champs ;
  • couper ce qui est trop long (timeout), servir une réponse gardée en cache ;
  • même idée qu'un HttpInterceptor d'Angular (RxJS, avant et après), mais côté serveur, autour de la méthode du contrôleur ;
  • pas pour décider l'accès (guard) ni pour vérifier un paramètre (pipe).

En résumé : avant next.handle(), avant la méthode ; dans .pipe(…), après ; tap pour regarder, map pour transformer.

Dans la vraie vie : de temps en temps ; un journal des requêtes, une mesure de durée, une enveloppe commune des réponses. Le cache, vendredi matin, est aussi un intercepteur, fourni par Nest.

La configuration

TP

Lire et vérifier la configuration

Le concept

La fiche de réglages d'un appareil, rangée à côté de lui : le même appareil sert dans plusieurs pièces, seule la fiche change. Une application lit ses réglages (port, base de données, secrets) dans son environnement plutôt que dans son code : le même code tourne sur votre poste, en test et en production.

Le fichier .env : une variable par ligne, NOM=valeur. Il n'est jamais enregistré dans Git (la CLI l'a déjà mis dans .gitignore) : il contient des mots de passe. On enregistre à sa place un .env.example, avec des valeurs d'exemple, pour dire quelles variables existent.

@nestjs/config : ConfigModule.forRoot({ isGlobal: true }) lit .env au démarrage et range ses variables ; isGlobal le rend visible partout. ConfigService les donne : config.get('PORT'), ou config.getOrThrow('PORT'), qui arrête tout si la variable manque. Les variables d'environnement du système passent avant celles du fichier : en production, on ne met pas de .env, on règle l'environnement.

validate : une fonction donnée à ConfigModule, qui vérifie toutes les variables au démarrage. Une variable absente ou fausse arrête l'application tout de suite, avec un message clair, au lieu d'une panne plus tard. On l'écrit avec les règles de class-validator, comme un DTO.

registerAs : regroupe des réglages sous un nom (mediatheque.cleApi) et les rend injectables avec leur type : @Inject(mediathequeConfig.KEY) config: ConfigType<typeof mediathequeConfig>.

Quand s'en servir :

  • tout ce qui change d'un environnement à l'autre (adresse de la base, ports, clés d'API, durées) : dans .env, lu par ConfigModule, jamais écrit dans le code ;
  • validate dès qu'une variable est indispensable : l'application refuse de démarrer, au lieu de planter à la première requête ;
  • ConfigService pour une valeur isolée ; registerAs pour les réglages d'un même domaine, injectés avec leur type ;
  • un secret (mot de passe, clé) : .env sur le poste ; en production, le gestionnaire de secrets de l'hébergeur.

En résumé : les réglages dans .env (jamais dans Git), lus par ConfigModule, vérifiés au démarrage, donnés par ConfigService.

Dans la vraie vie : une fois par projet, puis chaque fois qu'un réglage s'ajoute ; la vérification au démarrage évite les mises en production qui tombent faute d'une variable.

La gestion des erreurs

TP

Exceptions métier et filtres d'exception

Le concept

Le service après-vente d'un magasin : quel que soit le rayon où le problème est né, la réponse au client suit le même modèle (un numéro de dossier, une explication), et le détail technique reste dans les registres internes.

Les exceptions HTTP : toutes héritent de HttpException, qui porte un statut et un message. Nest les transforme en réponse JSON : {"message":…,"error":…,"statusCode":…}.

L'exception métier : une classe à soi, qui hérite d'une exception HTTP ; son nom dit ce qui s'est passé, son parent donne le statut.

L'erreur imprévue : une erreur qui n'est pas une HttpException (une base injoignable, un bug). Nest répond 500 avec "Internal server error", sans détail, et écrit l'erreur et sa pile d'appels dans le terminal : le client ne voit rien d'interne.

Le filtre d'exception : une classe @Catch(…) qui implémente ExceptionFilter et sa méthode catch(exception, host) ; elle fabrique elle-même la réponse. @Catch(HttpException) pour les exceptions HTTP, @Catch() sans argument pour toutes les erreurs. On le branche avec @UseFilters(…) ou app.useGlobalFilters(…).

Logger : log pour ce qui se passe normalement, warn pour une anomalie attendue (une requête refusée), error pour une panne, avec la pile d'appels ; debug et verbose pour le détail, qu'on n'affiche pas en production.

Quand s'en servir :

  • un refus prévu (introuvable, déjà prêté, données invalides) : une exception HTTP ;
  • une exception métier quand le même refus revient à plusieurs endroits, ou pour un nom qui dit le problème ;
  • un format d'erreur commun à toute l'API (pour le front) et les pannes au journal : un filtre global ;
  • un filtre sur un seul contrôleur quand ses erreurs doivent avoir une autre forme (une API publique pour des partenaires).

En résumé : des exceptions HTTP (ou métier) pour les refus prévus ; un filtre global pour donner à toutes les erreurs le même format et garder les détails dans le journal.

Dans la vraie vie : les exceptions tous les jours ; le filtre global, une fois par projet. Un format d'erreur unique est ce que demandent les équipes front-end : un seul code pour afficher toutes les erreurs.

La validation des données

TP

DTO de requête, DTO imbriqués, sérialisation et Zod

Le concept

Le même formulaire administratif que jeudi, avec trois raffinements : un formulaire pour les recherches (les cases de l'adresse), un formulaire dans le formulaire (le cadre « personne à contacter »), et le tampon « confidentiel » sur ce qui ne doit pas sortir du bureau.

Le DTO de requête : les paramètres d'adresse (?page=2&limit=5) se vérifient aussi avec un DTO, @Query() query: QueryCoursesDto. Ils arrivent en texte : @Type(() => Number) (de class-transformer) les convertit avant la vérification. Une valeur par défaut s'écrit dans la classe : page: number = 1. C'est la bonne réponse au piège de DefaultValuePipe : ?limit=deux est refusé (400).

Le DTO imbriqué : un champ qui contient un objet, avec ses propres règles. @ValidateNested() dit de vérifier l'intérieur, @Type(() => LecteurDto) en quelle classe le transformer. Le message d'erreur indique le chemin : lecteur.email.

La sérialisation : choisir ce qui sort. @Exclude() (de class-transformer) sur une propriété d'une classe de réponse, et ClassSerializerInterceptor (fourni par Nest) retire cette propriété de la réponse. On l'utilise pour ne jamais renvoyer une adresse, un mot de passe haché.

Le validateur maison : quand aucune règle ne convient (un numéro de SIRET, un code postal français), registerDecorator de class-validator crée sa propre règle, @IsSiret(). On en écrit rarement.

Standard Schema, nouveauté de NestJS 12 : au lieu d'une classe DTO, un schéma écrit avec Zod (ou Valibot, ArkType), une bibliothèque qui décrit des données en objets JavaScript ; le type TypeScript s'en déduit (z.infer). On le donne au paramètre, avec le pipe StandardSchemaValidationPipe :

class-validator reste le plus répandu dans les projets NestJS ; Zod se rencontre dans les équipes qui partagent les schémas entre le serveur et une application React.

Quand s'en servir :

  • des paramètres d'adresse (pagination, filtres, tri) : un DTO avec @Query() ;
  • un objet dans le corps (un lecteur, une adresse) : un DTO imbriqué, avec @ValidateNested() et @Type() ;
  • une donnée à ne jamais renvoyer (mot de passe haché, adresse e-mail) : une classe de réponse avec @Exclude() ;
  • une règle qu'aucun décorateur ne couvre (SIRET, code postal) : un validateur maison ;
  • un schéma Zod déjà partagé avec le front : Standard Schema ; sinon, les classes DTO restent le choix par défaut avec Nest, et Swagger les lit sans effort.

En résumé : @Query() avec un DTO et @Type(() => Number) pour les paramètres d'adresse ; @ValidateNested() et @Type() pour un objet dans l'objet ; @Exclude() et ClassSerializerInterceptor pour ce qui ne sort pas.

Dans la vraie vie : les DTO de requête (pagination, filtres) tous les jours ; les DTO imbriqués et la sérialisation souvent ; un validateur maison rarement.

PostgreSQL et TypeORM

TP

Un ORM : entités et repositories

Le concept

Un interprète entre deux personnes qui ne parlent pas la même langue : votre code parle en objets (un Course), PostgreSQL en tables et en SQL. L'ORM (Object-Relational Mapping) traduit dans les deux sens : save(course) devient un INSERT, une ligne de résultat devient un objet. Pendant la formation Node.js, vous l'avez fait avec Sequelize ; on prend ici TypeORM, l'ORM pour lequel Nest fournit un module officiel, @nestjs/typeorm.

L'entité : une classe marquée @Entity('courses'), dont chaque propriété marquée @Column() est une colonne de la table.

Décorateur La colonne
@PrimaryGeneratedColumn('uuid') la clé primaire, un UUID donné par PostgreSQL (sans 'uuid' : un entier 1, 2, 3…)
@Column({ length: 120 }) varchar(120) ; { type: 'text' }, { type: 'int' }, { default: false }…
@CreateDateColumn(), @UpdateDateColumn() les dates de création et de modification, remplies toutes seules

Le repository : l'objet qui lit et écrit une table. TypeOrmModule.forFeature([Course]) dans le module le rend injectable ; @InjectRepository(Course) le demande.

Méthode SQL
find({ where, order, skip, take }), findAndCount(…) SELECT … WHERE … ORDER BY … OFFSET … LIMIT … (et COUNT)
findOneBy({ id }) SELECT … WHERE id = …, ou null
create(données) puis save(objet) un objet, puis l'INSERT (ou l'UPDATE s'il a déjà un identifiant)
merge(objet, données) recopie des champs, sans écrire
remove(objet), delete({ … }) DELETE
count(), countBy({ … }) SELECT COUNT(*)

Les opérateurs : ILike('%nest%') (recherche sans tenir compte des majuscules), In([…]), MoreThan(…), IsNull().

TypeORM 1.x : la version 1.0 (mai 2026) a retiré les anciennes écritures : findOneById → findOneBy({ id }) ; where: { x: null } → where: { x: IsNull() } ; relations: ['lessons'] → relations: { lessons: true } ; plus de lecture automatique de .env. Une documentation ou une réponse en ligne d'avant 2026 peut montrer l'ancienne forme.

La connexion : TypeOrmModule.forRootAsync dans AppModule, construite avec ConfigService. autoLoadEntities reprend les entités déclarées par forFeature. synchronize: true crée et modifie les tables d'après les entités à chaque démarrage : pratique pour commencer, jamais en production (une propriété renommée, et la colonne et ses données disparaissent) ; les migrations prennent le relais en fin de journée.

Quand s'en servir :

  • une API qui lit et écrit ses propres tables : un ORM, des entités et leurs repositories ;
  • les méthodes du repository (find, findOneBy, save) pour le courant ; le QueryBuilder ou le SQL pour un rapport ou un regroupement ;
  • TypeORM, Prisma ou Drizzle : un choix fait une fois par projet ; TypeORM suit la manière de Nest (classes et décorateurs) ;
  • synchronize: true seulement pour commencer en local ; les migrations ensuite.

En résumé : une entité par table, un repository par entité, injecté avec @InjectRepository ; TypeOrmModule.forRootAsync pour la connexion, forFeature dans chaque module.

Dans la vraie vie : tous les jours ; c'est le cœur de la plupart des API. TypeORM et Prisma sont les deux ORM les plus courants avec Nest ; Drizzle, plus récent, gagne du terrain.
