Introduction à NestJS

NestJS : ce que c'est, à quoi il sert, d'où il vient

Le concept

Le principe : un restaurant. La salle prend les commandes (l'application web ou mobile), la cuisine les prépare (le serveur). NestJS organise la cuisine.

NestJS : un framework pour écrire la partie serveur d'une application (le back-end), en TypeScript, sur Node.js. Le serveur :

  • reçoit les requêtes des applications web et mobiles ;
  • applique les règles métier et vérifie qui a le droit de faire quoi ;
  • lit et écrit dans la base de données, appelle d'autres services (paiement, e-mails) ;
  • répond, le plus souvent en JSON.

Ce qu'on construit avec :

  • des API REST : des adresses qui renvoient du JSON ; c'est LearnHub ;
  • des API GraphQL : l'application demande les seuls champs dont elle a besoin ;
  • des serveurs temps réel (WebSockets) : une messagerie, des notifications ;
  • des microservices : de petits services qui s'envoient des messages (Kafka, RabbitMQ, NATS, gRPC) ;
  • des tâches de fond : l'e-mail de confirmation d'une commande, un traitement chaque nuit.

Des cas réels, d'après la liste officielle des utilisateurs :

  • des entreprises françaises : Société Générale, Decathlon, TotalEnergies, Capgemini, Sanofi ;
  • ailleurs : Adidas, BMW, Mercedes-Benz, IBM, GitLab, JetBrains, ByteDance (la maison mère de TikTok) ;
  • la liste ne dit ni pour quelle application ni à quelle échelle.

Pourquoi il a été créé (documentation officielle, « Philosophy ») :

  • Node.js avait d'excellentes bibliothèques, mais rien pour ranger le code d'une application qui grandit ;
  • NestJS apporte cette architecture, « fortement inspirée d'Angular », pour des applications faciles à tester et à maintenir.

Qui le fait :

  • Kamil Myśliwiec, son créateur, avec une petite équipe et la communauté ;
  • le code est libre : licence MIT, gratuit même pour un usage commercial ;
  • aucun grand groupe derrière, à la différence d'Angular (Google) ou de React (Meta) : le projet vit de ses sponsors et du support payant qu'il vend aux entreprises.

Sa place aujourd'hui (relevé le 12 novembre 2026) : 77 110 étoiles sur GitHub, plus qu'Express (69 673) ; environ 24 millions de téléchargements de @nestjs/core sur npm la semaine du 4 au 10 novembre.

En résumé : NestJS écrit la partie serveur d'une application, en TypeScript ; né en 2017 pour donner à Node.js l'architecture d'Angular, il tourne sur Express et il est libre.

Dans la vraie vie : on le rencontre surtout dans les API d'entreprise écrites en TypeScript, derrière une application Angular, React ou mobile ; sa documentation, docs.nestjs.com, reste ouverte pendant les trois jours.

Pourquoi NestJS : ce qu'Express laisse à votre charge

Le concept

Le principe : un terrain et des briques, ou le plan de l'immeuble.

  • Express donne le terrain et les briques : chaque équipe bâtit à sa façon, deux projets ne se ressemblent jamais ;
  • NestJS donne le plan : un étage par domaine, un accueil à chaque étage, un standard qui relie les bureaux ; un nouveau venu s'y retrouve le premier jour.

Des cas réels, des API qui vivent des années avec des équipes qui changent :

  • l'API d'une banque en ligne : comptes, virements, cartes, plafonds ;
  • le back-office d'un site marchand : commandes, stocks, remboursements, factures ;
  • l'API d'une plateforme de rendez-vous médicaux : praticiens, créneaux, patients ;
  • le bogue évité : la règle métier recopiée dans trois routes Express par trois personnes, dont une seule est corrigée le jour où la règle change ;
  • LearnHub est une API de ce genre : un catalogue, des comptes, des inscriptions.

Dans TaskFlow (formation Node.js), vous rangiez routes, contrôleurs et services par convention : rien ne vous y obligeait. À trois développeurs et deux ans de maintenance, chacun finit par ranger différemment.

Ce que NestJS change :

  • il impose une organisation : modules, contrôleurs, services ;
  • il fabrique et relie les objets à votre place : l'injection de dépendances ;
  • il tourne par-dessus Express : on retrouve les requêtes, les réponses et les middlewares qu'on connaît.

En résumé : Express donne les briques, NestJS donne le plan ; moins de « plomberie », et tout le monde range au même endroit.

Dans la vraie vie : c'est l'argument qui fait choisir NestJS pour une API qu'une équipe va faire vivre des années ; la notion suivante dit quand on prend autre chose.

NestJS ou un autre framework, et avec quoi l'assembler

Le concept

Le principe : on ne déménage pas à vélo, et on ne prend pas un camion pour aller chercher le pain. Le bon framework dépend de ce qu'on construit et de l'équipe qui le construit.

Des cas réels, tirés du guide de choix écrit par l'équipe de NestJS (Nest vs Fastify, Express and Hono) :

  • un service de quelques routes qui restera petit (un relais vers une autre API, un récepteur de webhooks, les notifications qu'envoie un service de paiement) : Fastify ou Hono, il n'y a rien à organiser ;
  • une API sur Cloudflare Workers, des serveurs répartis dans le monde au plus près des utilisateurs : Hono, conçu pour cela ;
  • une API qui va grandir, avec plusieurs développeurs, une base de données et des tâches de fond : NestJS ;
  • LearnHub est dans ce dernier cas : un catalogue, des comptes, des inscriptions, une base, des tests.

Les briques d'une application et le trajet d'une requête

Le concept

Le principe : une mairie. Chaque direction (l'état civil, l'urbanisme) a son accueil, qui reçoit les demandes, et ses bureaux, qui les traitent ; un standard met les bureaux en relation.

Des cas réels :

  • une banque : l'écran « Mes comptes » appelle /api/accounts ; un contrôleur reçoit la demande, un service lit les soldes ;
  • un site marchand : « Ajouter au panier » appelle /api/cart ; le service du panier demande au service des stocks si l'article est disponible ;
  • un back-office : le module des factures se sert de celui des clients ;
  • le bogue évité : le contrôleur de 2 000 lignes que personne n'ose plus modifier, où requêtes, calculs et accès aux données sont mélangés ;
  • dans LearnHub, aujourd'hui : le module des cours, son contrôleur et son service, dans cet ordre.

Dans une application NestJS :

  • le module, une direction : il regroupe un domaine (CoursesModule pour le catalogue, LessonsModule pour les leçons) ; l'application est un arbre de modules, avec AppModule à la racine ;
  • le contrôleur, l'accueil : il reçoit les requêtes HTTP d'une adresse (/api/courses), lit ce qu'elles contiennent et renvoie la réponse, sans faire le travail lui-même ;
  • le service (un provider, dans le vocabulaire de Nest), le bureau : il fait le travail (chercher, calculer, enregistrer) ; le contrôleur le reçoit tout fait, par injection de dépendances, le standard de la mairie.

Lundi, le trajet s'enrichit :

  • avant le contrôleur : des middlewares, des guards et des pipes ;
  • autour : des intercepteurs ;
  • en cas d'erreur : des filtres.

Comment le voir : au démarrage, Nest écrit dans le terminal chaque module chargé (InstanceLoader), chaque contrôleur (RoutesResolver) et chaque route (RouterExplorer). On les lira dans quelques minutes.

En résumé : un module par domaine ; dans chaque module, un contrôleur qui reçoit et un service qui travaille ; Nest relie le tout.

Dans la vraie vie : c'est le découpage de toutes les API NestJS ; devant un projet inconnu, on cherche d'abord ses modules (le dossier src/), puis les contrôleurs, qui donnent la liste des adresses.

Les décorateurs TypeScript

Ce que fait un décorateur

Le concept

Une étiquette collée sur un colis : « fragile », « à livrer au 3e étage ». Le colis ne change pas ; le transporteur lit l'étiquette et agit en conséquence.

Des cas réels, une règle écrite au-dessus de ce qu'elle protège, visible en lisant le code :

  • le back-office d'un site marchand : la route « rembourser une commande » porte « administrateurs seulement » ;
  • la connexion d'une banque en ligne : la route porte « 5 essais par minute au plus » ;
  • une API de réservation : le paramètre « dates du séjour » porte « à vérifier avant d'entrer » ;
  • le bogue évité : la vérification recopiée au début de chaque fonction, que la vingtième route oublie ;
  • dans LearnHub : @Controller('courses') et @Get(':id') dès aujourd'hui ; vos propres décorateurs au jour 3 (@Roles(), @Public()).

Un décorateur est une étiquette posée sur une classe, une méthode ou un paramètre : Nest les lit au démarrage et sait quoi faire de chaque classe (@Controller), de chaque méthode (@Get) et de chaque paramètre (@Param).

Un décorateur est une fonction : @Rayon('romans') au-dessus d'une classe appelle la fonction Rayon une seule fois, quand la classe est chargée, en lui passant la classe. Elle peut noter quelque chose sur la classe ou remplacer une méthode.

La fabrique de décorateurs : une fonction qui reçoit des paramètres et renvoie le décorateur. @Controller('courses') et @Get(':id') sont des fabriques : 'courses' est le paramètre, le décorateur renvoyé note l'adresse.

Les quatre places d'un décorateur :

Sur Ce que reçoit la fonction Exemples de Nest
une classe la classe @Module, @Controller, @Injectable
une méthode la classe, le nom de la méthode, son descripteur (de quoi la remplacer) @Get, @Post, @HttpCode, @UseGuards
une propriété la classe et le nom de la propriété @IsString, @Column (jours 1 et 2)
un paramètre la classe, la méthode et la position du paramètre @Param, @Body, @Query, @Inject

reflect-metadata : une bibliothèque qui range des informations sur une classe, comme un carnet de notes attaché à elle : Reflect.defineMetadata(clé, valeur, classe) pour écrire, Reflect.getMetadata(clé, classe) pour lire. Les décorateurs de Nest écrivent dans ce carnet ; Nest le lit au démarrage.

Comment Nest sait quoi injecter : avec l'option emitDecoratorMetadata de tsconfig.json, TypeScript note dans le carnet de chaque classe décorée le type des paramètres de son constructeur (clé design:paramtypes). Nest y lit « ce contrôleur veut un AppService » et le lui fournit. C'est pour cela qu'on écrit constructor(private readonly appService: AppService) sans jamais écrire new AppService().

Les réglages : "experimentalDecorators": true et "emitDecoratorMetadata": true dans tsconfig.json, déjà activés par la CLI.

En résumé : un décorateur est une fonction appelée au chargement de la classe ; il note des informations que Nest lit au démarrage.

Dans la vraie vie : on utilise les décorateurs de Nest tous les jours ; on en écrit soi-même rarement, et presque toujours en assemblant ceux de Nest (@Public(), @Roles(), @CurrentUser(), que vous écrirez au jour 3).

Le module, le contrôleur et les routes de lecture

Le concept

Le principe : un grand magasin. Un rayon par famille de produits (le module), à chaque rayon un comptoir (le contrôleur) où l'on demande « montrez-moi tout », « montrez-moi celui-ci » ; le comptoir ne fabrique rien, il lit la demande et rend la réponse.

Des cas réels, chaque domaine a son module (produits, commandes, clients), chaque adresse son contrôleur :

  • la page d'une catégorie sur un site marchand : GET /api/products?category=velos ;
  • la fiche d'un produit : GET /api/products/123 ;
  • le suivi d'une commande chez un transporteur : GET /api/orders/456 ;
  • premier bogue : /api/products/promotions, écrite après /api/products/:id, n'est jamais atteinte ;
  • second bogue : une fiche introuvable qui répond 200, vide, affiche une page blanche au lieu de « produit introuvable » ;
  • dans LearnHub : le catalogue des cours, la liste puis la fiche d'un cours.

nest g module courses : crée src/courses/courses.module.ts et l'ajoute aux imports d'AppModule. Le module regroupe tout ce qui concerne les cours.

nest g controller courses --no-spec : crée src/courses/courses.controller.ts et le déclare dans CoursesModule. --no-spec évite le fichier de test vide ; on écrira nos tests au jour 3.

@Controller('courses') : toutes les routes de la classe commencent par /courses.

@Get(), @Get(':id') : une méthode par route. :id est un paramètre d'adresse : dans /courses/42, il vaut '42'.

@Param('id') et @Query('search') : donnent à la méthode un morceau de l'adresse. @Param lit les paramètres du chemin (/courses/42), @Query ceux qui suivent le ? (/courses?search=nest). Ils arrivent toujours en texte : '42', pas 42.

Ce que renvoie la méthode : Nest l'envoie en réponse. Un objet ou un tableau part en JSON, avec le statut 200.

NotFoundException : on la lance (throw) quand la ressource n'existe pas ; Nest répond 404 avec le message donné : {"message":"…","error":"Not Found","statusCode":404}.

Le préfixe global : app.setGlobalPrefix('api') dans main.ts fait commencer toutes les routes par /api ; l'adresse d'une API se distingue ainsi de celle d'un site. Le versionnement (app.enableVersioning()) ajoute de même un numéro de version, /api/v1/courses, quand on doit faire vivre deux versions d'une API en même temps ; on n'en a pas besoin ici.

L'ordre des routes : Nest essaie les routes d'un contrôleur dans l'ordre où les méthodes sont écrites. Une route fixe (/livres/disponibles) écrite après une route à paramètre (/livres/:id) n'est jamais atteinte : disponibles est pris pour un identifiant. Une route fixe s'écrit donc avant les routes à paramètre.

Les modules globaux et dynamiques : un module marqué @Global() est visible partout sans être importé ; à garder pour ce qui sert vraiment à tous (la configuration). Un module dynamique se configure en l'important : ConfigModule.forRoot({ … }), TypeOrmModule.forRoot({ … }). On en importera plusieurs lundi.

import type : avec les réglages de Nest 12 (isolatedModules et emitDecoratorMetadata), un type qui n'existe qu'à la compilation (une interface) et qui sert dans la signature d'une méthode décorée doit s'importer avec import type. Sinon, la compilation échoue avec l'erreur TS1272.

En résumé : un module par domaine (nest g module), un contrôleur par adresse (nest g controller), une méthode décorée par route ; @Param et @Query donnent les morceaux de l'adresse, en texte.

Dans la vraie vie : tous les jours ; chaque nouvelle fonction d'une API commence par un module, un contrôleur et ses routes.

Créer, modifier, supprimer : le corps, les statuts, les erreurs

Le concept

Au guichet, certaines demandes arrivent avec un formulaire rempli : c'est le corps de la requête. Le guichet répond par un tampon : « accepté », « créé », « refusé ». Ce sont les statuts HTTP.

Des cas réels, l'application cliente décide quoi afficher d'après le statut (« adresse enregistrée », « trajet complet », « carte introuvable ») :

  • l'ajout d'une adresse de livraison sur un site marchand : POST, réponse 201 ;
  • le changement du nombre de voyageurs d'une réservation de train : PATCH ;
  • la suppression d'une carte bancaire enregistrée : DELETE, réponse 204 ;
  • le bogue classique : l'API qui répond 200 à une erreur ; l'écran affiche « enregistré » alors que rien n'a été créé ;
  • dans LearnHub : un formateur crée, modifie et supprime ses cours.

@Post(), @Patch(':id'), @Delete(':id') : créer, modifier une partie, supprimer. (@Put remplace une ressource entière ; on lui préfère @Patch, qui ne change que les champs envoyés.)

@Body() : donne à la méthode le corps JSON de la requête, déjà transformé en objet.

Omit<Livre, 'id'> : le type Livre sans id (c'est le serveur qui le donne) ; Partial<…> : tous les champs deviennent facultatifs, pour une modification. Deux outils de TypeScript vus pendant la formation React.

Les statuts par défaut : 200 pour une lecture, 201 Created pour un POST. @HttpCode(204) change le statut d'une route : 204 No Content, « fait, rien à renvoyer », pour une suppression.

Les exceptions HTTP : on les lance, Nest répond le statut correspondant.

Exception Statut Quand
BadRequestException 400 la requête est mal formée
UnauthorizedException 401 pas connecté (jour 3)
ForbiddenException 403 connecté, mais pas le droit (jour 3)
NotFoundException 404 la ressource n'existe pas
ConflictException 409 conflit : déjà emprunté, adresse déjà utilisée

En résumé : @Body() pour le corps, 201 automatique pour un POST, @HttpCode(204) pour une suppression, une exception pour chaque refus.

Dans la vraie vie : tous les jours ; les statuts justes comptent, car les applications clientes (une page React, une application mobile) décident quoi afficher d'après eux.

Le service et l'injection de dépendances

Le concept

Le principe : au restaurant, le serveur prend la commande et l'apporte, mais ne cuisine pas ; il ne choisit pas non plus son cuisinier, le restaurant le lui affecte. Le contrôleur est le serveur, le service la cuisine, Nest le restaurant.

Des cas réels, du code métier demandé par plusieurs écrans :

  • le total d'un panier : la page panier, la commande, l'application mobile ;
  • le contrôle d'un virement (plafond, solde), déclenché par trois écrans d'une banque en ligne ;
  • l'e-mail de confirmation d'une plateforme de réservation ;
  • le code métier vit à un seul endroit, le service, et chaque contrôleur le reçoit tout fait ;
  • le bogue évité : le total calculé dans deux contrôleurs, deux montants différents après une promotion, ou deux catalogues en mémoire qui s'ignorent ;
  • dans LearnHub : le catalogue passe dans CoursesService, que le contrôleur reçoit par injection.

Le service : une classe marquée @Injectable(), qui porte la logique et les données d'un domaine. Le contrôleur ne garde plus que la lecture de la requête et la réponse.

nest g service courses --no-spec : crée src/courses/courses.service.ts et le déclare dans les providers de CoursesModule.

L'injection par le constructeur : le contrôleur demande le service dans son constructeur, par son type. Nest le fabrique et le lui donne :

private readonly crée en même temps la propriété this.livresService ; on ne fait jamais new LivresService().

L'inversion de contrôle : ce n'est plus la classe qui crée ce dont elle a besoin, c'est le conteneur de Nest qui crée tout et relie les objets entre eux. Le conteneur fabrique chaque service une seule fois et donne la même instance à tous ceux qui la demandent : un seul catalogue pour toute l'application.

Pourquoi c'est utile :

Sans injection Avec injection
new LivresService() dans chaque contrôleur : plusieurs catalogues différents une seule instance, partagée
pour tester le contrôleur, on garde le vrai service dans un test, on donne un faux service à la place (jour 3)
changer de service oblige à modifier chaque new on change la déclaration du module, une seule fois

En résumé : @Injectable() sur le service, providers: [LeService] dans le module, et le service demandé dans le constructeur du contrôleur.

Dans la vraie vie : tous les jours ; dans une API NestJS, les contrôleurs sont courts et le code métier est dans les services.

Providers personnalisés et cycle de vie

Le concept

Le standard d'une entreprise : on demande « la comptabilité », pas « Mme Martin, bureau 214 ». Le nom du service suffit ; le standard sait qui répond.

Des cas réels :

  • une valeur de réglage : la durée d'un prêt en médiathèque, d'une location de vélo en libre-service ;
  • un objet fabriqué au démarrage : le client d'un service de paiement, avec la clé de l'environnement ;
  • une valeur remplacée dans les tests : l'heure courante d'un calcul de pénalités de retard ;
  • au démarrage : charger les données de départ, vérifier une connexion avant la première requête ;
  • le bogue évité : un new Date() écrit en dur, impossible à tester, ou une constante recopiée dans dix fichiers dont un seul est mis à jour ;
  • dans LearnHub : le catalogue de départ, fourni sous un jeton et chargé au démarrage.

Dans Nest, chaque provider est rangé sous un jeton : sa classe le plus souvent, ou un nom qu'on choisit.

Le provider de classe : providers: [LivresService] est le raccourci de { provide: LivresService, useClass: LivresService } : le jeton est la classe, Nest fabrique une instance.

useValue : une valeur toute faite, rangée sous un jeton texte.

Pratique pour une constante de configuration, un catalogue de départ ou, dans un test, un faux service.

useFactory : une fonction qui fabrique la valeur au démarrage ; elle peut recevoir d'autres providers (inject: [...]).

Pratique pour un objet qui dépend de la configuration (un client d'API, une connexion).

@Inject('JETON') : demander un provider rangé sous un jeton texte, puisqu'il n'a pas de classe pour servir de type :

Les portées : par défaut, une seule instance pour toute l'application (singleton) ; c'est presque toujours ce qu'on veut.

Portée Une instance… Quand
DEFAULT (singleton) pour toute l'application presque toujours
REQUEST par requête HTTP une donnée propre à la requête (rare, et plus lent)
TRANSIENT à chaque injection un objet qu'on ne veut pas partager (rare)

Le cycle de vie, des méthodes que Nest appelle aux moments clés, si la classe les possède :

  • onModuleInit() : le module est prêt, avant la première requête ; on y charge des données, on vérifie une connexion ;
  • onModuleDestroy() : à l'arrêt, avec app.enableShutdownHooks() ; on y ferme ce qu'on a ouvert.

Les dépendances circulaires : A demande B et B demande A ; Nest ne sait pas lequel fabriquer en premier et refuse de démarrer. forwardRef(() => B) débloque, mais c'est presque toujours le signe qu'il faut un troisième service.

Logger : le journal de Nest, celui des lignes [Nest] … LOG …. new Logger(MonService.name) écrit des messages précédés du nom du service, avec la date ; on le préfère à console.log.

En résumé : un jeton, une façon de fournir (useClass, useValue, useFactory) ; @Inject('JETON') quand le jeton est un texte ; onModuleInit pour agir au démarrage.

Dans la vraie vie : useValue et useFactory reviennent surtout dans la configuration (lundi) et dans les tests (vendredi) ; onModuleInit, de temps en temps ; les portées autres que la portée par défaut, rarement.

Les portées : une instance pour l'application, par requête ou par consommateur

Le concept

Le principe : par défaut, Nest fabrique chaque provider une fois, au démarrage, et le donne à tous ceux qui le demandent. Une portée change cette durée de vie : une instance par requête HTTP, ou une instance pour chaque classe qui la demande.

Des cas réels :

  • un SaaS avec une base de données par client : la connexion dépend du client de la requête (un en-tête, un sous-domaine) ; c'est l'exemple que prend la documentation de Nest (portées d'injection) ;
  • GraphQL : un DataLoader regroupe et met en cache les lectures ; il se crée par requête, sinon les données mises en cache pour un utilisateur ressortent dans la requête d'un autre (DataLoader) ;
  • un journal qui préfixe chaque ligne par le nom de la classe qui écrit : une instance par classe consommatrice ;
  • le bogue évité : l'utilisateur courant rangé dans une propriété d'un service singleton ; deux requêtes se chevauchent (un await suffit), la seconde écrase la première, et un client lit les données d'un autre ;
  • dans LearnHub : tout reste en portée par défaut ; l'utilisateur connecté (vendredi) se lira dans la requête, jamais dans une propriété de service.

Les trois portées, posées dans @Injectable({ scope: Scope.REQUEST }) :

Portée Une instance… Remonte la chaîne Coût Quand
Scope.DEFAULT pour toute l'application, créée au démarrage non aucun presque toujours
Scope.REQUEST par requête, jetée après la réponse oui : ce qui l'injecte devient « par requête », contrôleur compris toute la chaîne refabriquée à chaque requête une donnée propre à la requête : le client, un DataLoader
Scope.TRANSIENT pour chaque classe qui la demande non une instance par consommateur un objet réglé pour son consommateur : un journal

Ce qui va avec :

  • @Inject(REQUEST) (de @nestjs/core) : la requête Express, dans un provider de portée REQUEST ;
  • @Inject(INQUIRER) : dans un provider TRANSIENT, la classe qui l'a demandé (son nom, pour le journal) ;
  • durable: true, avec une ContextIdStrategy : une instance par client plutôt que par requête ; le SaaS multi-clients sans tout refabriquer à chaque requête ;
  • AsyncLocalStorage de Node.js, souvent par la bibliothèque nestjs-cls : la donnée de la requête lisible partout, sans changer la portée de personne ; la documentation de Nest en fait une recette (Async Local Storage) ; c'est l'alternative courante à REQUEST.

En résumé : portée par défaut pour presque tout ; REQUEST remonte jusqu'au contrôleur et coûte à chaque requête ; TRANSIENT donne une instance à chaque consommateur ; pour transporter une donnée de requête, AsyncLocalStorage d'abord.

Dans la vraie vie : rarement ; on reste en portée par défaut et on passe la donnée de la requête en paramètre, ou par AsyncLocalStorage ; REQUEST et durable servent surtout au multi-clients et aux DataLoader de GraphQL.

Les DTO

TP

Vérifier ce que le client envoie : DTO et ValidationPipe

Le concept

Un formulaire administratif : des cases précises, des règles (« date au format JJ/MM/AAAA », « champ obligatoire ») ; un dossier mal rempli revient avec la liste des cases à corriger, avant d'arriver au bureau qui le traite.

Des cas réels :

  • le formulaire d'inscription d'un site : « 8 caractères minimum », « adresse e-mail invalide » ;
  • une commande de repas livrés : une quantité entière, positive ;
  • la saisie d'un virement : un montant, un IBAN au bon format ;
  • l'écran vérifie déjà, mais l'API ne peut pas lui faire confiance : n'importe qui l'appelle directement, avec curl ou un script ;
  • le DTO refuse ce qui ne suit pas les règles, avec la liste des erreurs, avant que la donnée n'atteigne le service ;
  • le bogue évité : la commande de « -3 pizzas » enregistrée, ou le cours sans titre créé par la dernière commande de l'exercice 1.4-B ;
  • dans LearnHub : chaque cours créé ou modifié passe par son DTO.

Le DTO (Data Transfer Object, l'objet qui transporte les données) est ce formulaire : la liste des champs qu'un client a le droit d'envoyer, et leurs règles.

Le DTO est une classe, pas une interface : une interface disparaît à la compilation, alors qu'une classe existe encore quand l'application tourne, avec les décorateurs de ses propriétés. C'est ce qui permet de vérifier les données à chaque requête.

class-validator : des décorateurs de règles, posés sur les propriétés du DTO.

Décorateur Règle
@IsString(), @IsInt(), @IsBoolean() le type de la valeur
@IsNotEmpty() pas de texte vide
@MaxLength(120), @Min(0), @Max(2100) les limites
@IsEmail(), @IsUUID(), @IsIn([...]) un format, une liste de valeurs
@IsOptional() le champ peut manquer ; ses autres règles ne s'appliquent que s'il est présent

Chaque règle accepte un message à la place du message anglais : @IsNotEmpty({ message: 'Le titre est obligatoire' }).

ValidationPipe : vérifie chaque corps reçu d'après son DTO, avant la méthode du contrôleur ; s'il y a une erreur, la requête s'arrête avec un 400 et la liste des problèmes. On le branche une fois pour toute l'application, dans main.ts :

  • whitelist : retire les champs que le DTO ne connaît pas ;
  • forbidNonWhitelisted : refuse plutôt la requête (une faute de frappe se voit tout de suite) ;
  • transform : donne au contrôleur une vraie instance du DTO, grâce à class-transformer, installé avec class-validator.

PartialType : le DTO de modification à partir de celui de création, avec les mêmes règles, tous les champs devenus facultatifs : class UpdateCourseDto extends PartialType(CreateCourseDto) {}. Il existe dans @nestjs/mapped-types et dans @nestjs/swagger ; celui de @nestjs/swagger garde en plus la documentation.

DTO, entité, interface :

Ce que c'est Exemple
DTO ce qui entre (ou sort) par l'API, avec ses règles CreateCourseDto : un titre obligatoire, un prix positif
Entité ce qui est enregistré en base (lundi) Course, avec son identifiant et ses dates
Interface une forme connue de TypeScript seulement Course d'aujourd'hui, en mémoire

Un DTO de réponse sert à ne pas tout renvoyer : un utilisateur sans son mot de passe, par exemple (jour 3).

Le piège des champs absents : avec transform, un champ facultatif que le client n'a pas envoyé existe quand même dans l'instance du DTO, avec la valeur undefined. Un { disponible: true, ...dto } le remet donc à undefined. Les valeurs par défaut s'écrivent avec ?? : dto.disponible ?? true.

En résumé : une classe DTO par corps reçu, des décorateurs de règles sur ses propriétés, ValidationPipe dans main.ts ; une requête mal formée s'arrête à 400 avec le détail.

Dans la vraie vie : tous les jours ; chaque route qui reçoit un corps a son DTO. C'est la première protection d'une API : on ne fait jamais confiance à ce qu'envoie le client.

Composer les DTO, nettoyer les entrées, placer chaque règle

Le concept

Le principe : un DTO se dérive d'un autre au lieu d'être recopié ; une valeur se nettoie avant d'être vérifiée ; une règle qui dépend de ce qui est déjà enregistré ne va pas dans le DTO, mais dans le service.

Des cas réels :

  • l'inscription et le profil d'un site : le même formulaire, sans le mot de passe pour le profil (OmitType), avec le mot de passe seul pour la page qui le change (PickType) ;
  • une adresse e-mail saisie « Lea.Martin@Example.COM » sur un téléphone : nettoyée (espaces, minuscules) avant d'être vérifiée, sinon deux comptes pour la même personne ;
  • une facture : le numéro de TVA obligatoire seulement pour une entreprise (@ValidateIf) ;
  • le bogue évité : cette règle laissée dans le DTO d'une modification partielle ; PartialType la rend facultative, et une entreprise sans numéro de TVA passe ;
  • dans LearnHub : UpdateCourseDto est déjà un PartialType ; une règle qui croise deux champs d'un cours se vérifierait dans CoursesService.update, sur le cours complet.

Composer, avec les fonctions de @nestjs/mapped-types ou de @nestjs/swagger (celles de Swagger gardent la documentation) :

Fonction Donne Exemple
PartialType(A) les champs de A, tous facultatifs une modification (PATCH)
PickType(A, ['x']) seulement x, avec ses règles le changement de mot de passe
OmitType(A, ['x']) tout sauf x le profil, sans le mot de passe
IntersectionType(A, B) les champs de A et ceux de B une commande avec son adresse de livraison

Elles se combinent : PartialType(OmitType(InscriptionDto, ['motDePasse'])).

@Transform (de class-transformer) : une fonction appliquée au champ quand le JSON devient une instance du DTO, donc avant les règles : trim(), minuscules, conversion.

@ValidateIf(condition) : les règles du champ ne s'appliquent que si la condition est vraie.

Où placer chaque règle :

  • la forme d'un champ (type, longueur, format) : le DTO ;
  • deux champs de la même requête, en création : le DTO, avec @ValidateIf ;
  • ce qui dépend de l'état enregistré, ou d'une modification partielle : le service, sur l'objet complet, avec une BadRequestException ou une ConflictException.

Les options de ValidationPipe qui comptent pour le front :

Option Effet Quand
errorHttpStatusCode: 422 422 au lieu de 400 si le front ou les règles de l'entreprise l'attendent
stopAtFirstError: true une seule erreur par champ des messages courts sous chaque champ
exceptionFactory fabrique l'erreur à partir de la liste des erreurs les erreurs rangées par champ, pour les afficher sous chaque contrôle d'un formulaire Angular ; le format commun à toutes les erreurs vient lundi, avec les filtres d'exception
disableErrorMessages: true un 400 sans le détail une API publique où le détail en dirait trop

En résumé : on compose les DTO (PartialType, PickType, OmitType, IntersectionType), on nettoie avec @Transform, on conditionne avec @ValidateIf, et la règle qui croise l'état enregistré va dans le service.

Dans la vraie vie : PartialType tous les jours, PickType et OmitType souvent ; @Transform pour les e-mails et les textes saisis ; la règle croisée dans le service, toujours ; exceptionFactory une fois par projet, souvent remplacée par un filtre global.

Un module qui en utilise un autre : les leçons

Le concept

Le principe : deux directions d'une mairie qui travaillent ensemble ; l'urbanisme a besoin de l'état civil pour vérifier une identité. L'état civil doit accepter de rendre ce service, et l'urbanisme doit savoir à qui s'adresser.

Des cas réels, chaque module garde son domaine et ne partage que ce qu'il exporte :

  • un site marchand : le module des commandes demande au module des stocks s'il reste l'article ;
  • une banque en ligne : le module des virements demande au module des comptes le solde disponible ;
  • une plateforme de réservation : le module des avis vérifie auprès de celui des séjours que le client a bien séjourné ;
  • le bogue évité : le module des commandes qui recalcule lui-même le stock et oublie une règle que seul le service des stocks connaissait (les articles déjà réservés) ;
  • dans LearnHub : les leçons demandent au service des cours si le cours existe.

exports : un module garde ses providers pour lui, sauf ceux qu'il exporte. exports: [CoursesService] rend le service des cours utilisable ailleurs.

imports : un module qui a besoin d'un service d'un autre module importe ce module : imports: [CoursesModule].

La ressource imbriquée : les leçons appartiennent à un cours ; leurs adresses le disent : GET /api/courses/:courseId/lessons. Le contrôleur des leçons s'écrit @Controller('courses/:courseId/lessons').

L'erreur « Nest can't resolve dependencies » : la plus fréquente des débuts avec Nest. Elle dit quel provider n'a pas pu être fabriqué, quel paramètre manque, et dans quel module :

Trois causes, dans l'ordre où les vérifier : le service n'est pas dans les providers de son module ; il n'est pas dans ses exports ; son module n'est pas dans les imports du module qui le demande.

En résumé : on exporte ce qu'on partage, on importe le module dont on a besoin ; une ressource qui appartient à une autre a son adresse sous la sienne.

Dans la vraie vie : tous les jours ; et l'erreur « can't resolve dependencies » se lit en trois secondes une fois qu'on sait où regarder.

Angular et Nest : la même injection, d'autres règles

Le concept

Le principe : Nest a repris d'Angular le vocabulaire de l'injection (modules, @Injectable, providers, jetons) ; presque tous vos réflexes d'Angular marchent, et ceux qui ne marchent pas font les bogues des premières semaines.

Des cas réels :

  • un développeur Angular qui rejoint l'équipe de l'API retrouve @Injectable, useFactory, @Optional() et forwardRef() ;
  • son premier réflexe devant « Nest can't resolve dependencies » : déclarer le service dans les providers du module qui en a besoin ; en Angular, avec providedIn: 'root', c'est sans conséquence ; en Nest, c'est une seconde instance, avec ses propres données ;
  • le bogue évité : deux catalogues en mémoire qui s'ignorent, deux pools de connexions à la base, deux caches qui se contredisent ;
  • dans LearnHub : CoursesModule exporte son service et LessonsModule importe CoursesModule (la partie précédente) ; ci-dessous, ce que donne le réflexe d'Angular.

Ce qui est pareil, ce qui change :

En Angular En Nest Ce qui change
@Injectable({ providedIn: 'root' }) providers du module, exports, puis imports dans les modules qui s'en servent ; @Global() pour ce qui sert partout rien n'est visible hors de son module par défaut
providers d'un composant : une instance par composant pas d'injecteur par composant ; le même provider déclaré dans deux modules : deux instances une instance par application, sauf portée REQUEST ou TRANSIENT
InjectionToken<T> un texte ou un Symbol : @Inject('DUREE_PRET_JOURS') le jeton ne porte pas de type : on type le paramètre soi-même
useClass, useValue, useFactory avec deps, useExisting les mêmes, avec inject: [...] à la place de deps pas de multi: true
la fonction inject() le constructeur pas de fonction inject() dans Nest 12
@Optional(), forwardRef() les mêmes rien
ngOnInit, ngOnDestroy, provideAppInitializer onModuleInit, onApplicationBootstrap, onModuleDestroy, onApplicationShutdown elles peuvent être async : Nest attend leur fin avant d'ouvrir le port
pipe, guard, intercepteur les mêmes mots, d'autres rôles (lundi) un pipe vérifie ou transforme une entrée ; un guard laisse passer ou refuse une requête ; un intercepteur entoure l'appel de la méthode

Partir d'un contrat Swagger : l'animalerie

Générer une API NestJS à partir d'un contrat

Le concept

Le principe : le plan d'architecte livré avant les travaux. Le contrat, un fichier OpenAPI (l'ancien « Swagger »), décrit chaque route ; le générateur pose les murs (contrôleurs, modèles), vous aménagez les pièces (le code métier).

Des cas réels :

  • un partenaire impose son contrat : un service de paiement, un transporteur ;
  • l'équipe mobile et l'équipe API fixent le contrat ensemble, puis avancent chacune de leur côté ;
  • le bogue évité : une route écrite à la main qui s'écarte du contrat (un champ renommé), et l'application du partenaire qui casse ;
  • ici : l'exemple officiel de Swagger, Swagger Petstore, une animalerie (des animaux, dont « doggie »), dans un dossier à part.

Deux outils :

Outil Ce qu'il produit à partir du contrat Ses limites
OpenAPI Generator, générateur typescript-nestjs-server le squelette NestJS : un contrôleur par groupe de routes, une classe abstraite à implémenter par groupe, les modèles, et un ApiModule.forRoot() à importer dans une application créée par nest new en bêta ; demande Java (ou Docker) ; modèles en interfaces, donc sans validation ; imports sans .js, à corriger en ESM ; Express seulement
openapi-typescript les types TypeScript du contrat, dans un fichier .d.ts ; Node.js suffit les types seuls : contrôleurs et DTO s'écrivent à la main ; un DTO qui les implémente (implements) est vérifié par TypeScript

Garder le contrat : à chaque modification, comparer le /docs-json produit par NestJS au contrat, dans l'intégration continue ; oasdiff signale les changements qui casseraient les clients.

En résumé : le contrat d'abord, c'est nest new, le contrat, le générateur, puis l'implémentation ; le code d'abord, c'est @nestjs/swagger, comme LearnHub.

Dans la vraie vie : de temps en temps, quand le contrat est imposé ou partagé entre équipes ; le code généré se relit toujours (générateur en bêta, imports à corriger en ESM).
